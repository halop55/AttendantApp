# Attendance Backend (`attendanceBE`)

## 1. Project Overview

`attendanceBE` is the Express API for the company attendance application. It is responsible for authenticating API requests, deriving the employee email from the authenticated identity, and reading/writing attendance records in Supabase.

| Area | Current implementation |
| --- | --- |
| Runtime | Node.js, CommonJS output |
| Language | TypeScript in `src/`, compiled to `dist/` |
| HTTP framework | Express 5 |
| Database client | `@supabase/supabase-js` |
| Validation/config | `dotenv` + `zod` |
| Token verification | `jose` with Firebase securetoken JWKS and Logto JWKS |
| Containerization | Multi-stage Dockerfile + docker-compose |

Main responsibilities:

- Expose attendance API routes under `/api/v1/attendance`.
- Protect attendance routes with token middleware.
- Support Firebase Auth ID tokens from the frontend employee login flow.
- Keep compatibility with existing Logto JWT verification.
- Support local dev bypass mode for Supabase testing.
- Persist attendance data in the Supabase `attendance_logs` table.

This backend does not render UI and does not create Firebase accounts. Firebase employee account creation happens in the frontend through Firebase Auth and Firestore.

## 2. Architecture

### High-level architecture

```text
Expo frontend
  Firebase Auth session
  axios Authorization: Bearer <Firebase ID token>
        |
        v
Express API (`attendanceBE`)
  CORS middleware
  JSON parser
  attendance router
  verifyAccessToken middleware
        |
        v
AttendanceController
        |
        v
AttendanceService
        |
        v
AttendanceRepository
        |
        v
Supabase table: attendance_logs
```

### Request flow

```text
client request
  -> src/server.ts creates app and listens on env.PORT
  -> src/app.ts applies CORS and express.json()
  -> /api/v1/attendance mounted to attendanceRouter
  -> attendance.route.ts applies verifyAccessToken([])
  -> jwt.middleware.ts verifies Firebase or Logto token
  -> req.auth.email becomes the employee identity
  -> attendance.controller.ts validates auth/email/body shape
  -> attendance.service.ts applies attendance business rules
  -> attendance.repository.ts performs Supabase query/mutation
  -> JSON response: { success, data } or { success: false, message }
```

### Authentication flow

The middleware supports three modes:

1. **Firebase token mode**: If a Bearer token has issuer `https://securetoken.google.com/...`, it is verified against Google securetoken JWKS. The backend requires:
   - `aud` equals `FIREBASE_PROJECT_ID`
   - `iss` equals `https://securetoken.google.com/${FIREBASE_PROJECT_ID}`
   - token contains a non-empty `email`
2. **Logto token mode**: Non-Firebase tokens are verified against `${LOGTO_ENDPOINT}/oidc/jwks` and checked against `LOGTO_AUDIENCE`. Required scopes are supported by the middleware, though current routes pass an empty scope list.
3. **Development bypass mode**: If `BYPASS_AUTH=true` and the request has no `Authorization` header, the middleware injects a fixed dev identity:
   - email: `test@company.com`
   - scopes: `attendance:read`, `attendance:write`

Important: if an `Authorization` header is present, bypass mode does not override it. This allows the frontend to send real Firebase tokens even when local bypass remains enabled.

### Backend/frontend interaction

The frontend calls:

- `GET /health`
- `GET /api/v1/attendance/today`
- `POST /api/v1/attendance/check-in`
- `POST /api/v1/attendance/check-out`

For protected attendance calls, the frontend sets:

```http
Authorization: Bearer <Firebase ID token>
Content-Type: application/json
```

## 4. Startup Flow

### Development startup

```text
npm run dev
  -> ts-node-dev --respawn --transpile-only src/server.ts
  -> src/server.ts imports env
  -> env.ts loads .env and validates it with zod
  -> createApp() builds Express middleware/routes
  -> app.listen(env.PORT)
```

### Production startup

```text
npm run build
  -> TypeScript compiles src/ to dist/

npm start
  -> node dist/server.js
  -> compiled server listens on PORT
```

### Initialization order

1. `dotenv.config()` reads `.env`.
2. `envSchema.parse(process.env)` validates required environment variables.
3. `supabase.ts` creates a Supabase client when imported.
4. `jwt.middleware.ts` creates remote JWKS clients for Logto and Firebase.
5. `app.ts` creates Express middleware and routes.
6. `server.ts` listens on `env.PORT`.

## 5. API Flow

### API endpoints

| Method | Path | Auth | Request body | Success response | Notes |
| --- | --- | --- | --- | --- | --- |
| `GET` | `/health` | No | None | `{ success: true, message, service }` | Public health check. |
| `GET` | `/api/v1/health` | No | None | `{ success: true, message, service }` | API-prefixed alias. |
| `GET` | `/api/v1/attendance/today` | Yes | None | `{ success: true, data }` | Returns latest row today for `req.auth.email`, or `null`. |
| `POST` | `/api/v1/attendance/check-in` | Yes | `{ "note"?: string }` | `201 { success: true, data }` | Creates new row if employee has not checked in today. |
| `POST` | `/api/v1/attendance/check-out` | Yes | `{ "note"?: string }` | `200 { success: true, data }` | Updates latest open row where `checkout_at IS NULL`. |

### Request lifecycle

1. CORS headers are applied for all requests:
   - `Access-Control-Allow-Origin: *`
   - `Access-Control-Allow-Methods: GET,POST,PUT,PATCH,DELETE,OPTIONS`
   - `Access-Control-Allow-Headers: Content-Type, Authorization`
2. `OPTIONS` returns `204`.
3. `express.json()` parses request bodies.
4. Attendance routes pass through `verifyAccessToken([])`.
5. Controller extracts `req.auth.email`.
6. Service performs business checks.
7. Repository calls Supabase.
8. Controller returns JSON.

### Error response format

Auth middleware:

```json
{
  "success": false,
  "message": "Unauthorized"
}
```

Controller/service/repository errors:

```json
{
  "success": false,
  "message": "Employee already checked in today"
}
```

## 6. Authentication System

### Firebase Auth ID tokens

The frontend signs in users through Firebase Auth and sends an ID token in the `Authorization` header. Backend verification happens in `verifyFirebaseToken()`:

```text
decodeJwt(token)
  -> issuer starts with https://securetoken.google.com/
  -> jwtVerify(token, firebaseJwks, { audience, issuer })
  -> require payload.sub
  -> require payload.email
  -> req.auth = { sub, email, scopes, audience }
```

The backend does not store Firebase sessions. It only verifies the signed ID token per request.

### Logto compatibility

Logto verification remains available for non-Firebase tokens:

```text
jwtVerify(token, logtoJwks, { issuer: `${LOGTO_ENDPOINT}/oidc` })
  -> verify aud contains LOGTO_AUDIENCE
  -> verify sub exists
  -> verify required scopes if a route passes them
```

### Development bypass

`BYPASS_AUTH=true` only applies when the request has no `Authorization` header. This is useful for local Supabase testing and for health-checking protected endpoints without a Firebase account. It should not be enabled in production.

## 7. Database / Backend Logic

### Supabase table inferred from code

The repository uses one table:

```text
attendance_logs
├── id              number
├── employee_email  string
├── checkin_at      timestamp/string nullable
├── checkout_at     timestamp/string nullable
├── note            string nullable
└── created_at      timestamp/string (returned by Supabase, not declared in local type)
```

No migrations or SQL schema files are currently present in this repository. The schema above is inferred from `attendance.repository.ts` and observed API responses.

### Business rules

| Rule | Implemented in | Behavior |
| --- | --- | --- |
| Normalize employee email | `AttendanceService.normalizeEmail()` | `trim().toLowerCase()` before queries/mutations. |
| One check-in per UTC day | `AttendanceService.checkIn()` + `findTodayByEmail()` | If a row exists today with `checkin_at`, returns `409`. |
| Checkout requires an open row | `AttendanceService.checkOut()` + `checkOutLatestOpenLog()` | If no `checkout_at IS NULL` row exists, returns `400`. |
| Today's record uses UTC boundaries | `toUtcDayBounds()` in repository | Uses UTC day start/end, not local timezone. |
| Checkout updates latest open log | `findOpenLogByEmail()` order descending | Latest `checkin_at` open row is updated. |

### Supabase access model

The backend currently uses `SUPABASE_ANON_KEY`. Any Row Level Security policy in Supabase must allow the required select/insert/update operations for this anon key or the backend will return repository errors.

## 9. Important Features

### Health endpoint

Implemented in `src/app.ts`. It is public and useful for:

- frontend connectivity checks
- Docker/container readiness checks
- local troubleshooting

### Firebase-backed employee identity

The backend trusts only verified Firebase ID tokens. Employee identity for attendance is the token `email`.

### Attendance check-in

`POST /api/v1/attendance/check-in`

1. Auth middleware sets `req.auth.email`.
2. Controller rejects missing email.
3. Service normalizes email.
4. Repository checks today's record.
5. If already checked in, service throws `409`.
6. Repository inserts `{ employee_email, note, checkin_at }`.

### Attendance check-out

`POST /api/v1/attendance/check-out`

1. Auth middleware sets `req.auth.email`.
2. Service finds latest open log.
3. If no open log exists, service throws `400`.
4. Repository updates `checkout_at` and `note`.

### Today's attendance

`GET /api/v1/attendance/today` returns the latest record where `checkin_at` is within the current UTC day.

## 10. Error Handling

### Current patterns

- Middleware uses `AuthorizationError` with explicit status codes.
- Controllers use `try/catch` and return `{ success: false, message }`.
- Service methods throw `Error` objects and attach `statusCode` for expected business errors.
- Repository wraps Supabase errors in contextual messages such as `findTodayByEmail failed: ...`.

### Logging

- `server.ts` logs the listening port using `console.log`.
- `attendance.controller.ts` currently logs `req.auth` on check-in.
- `pino` and `pino-http` are installed but not wired into `app.ts`.

Security note: avoid logging full auth payloads or tokens in production. If request logging is added, redact `Authorization`.

## 11. Coding Rules

Follow the current layered pattern:

```text
route -> middleware -> controller -> service -> repository -> external database
```

Rules for future work:

- Keep Express request/response code in controllers.
- Keep business rules in services.
- Keep Supabase queries in repositories.
- Keep auth and cross-cutting request checks in `src/shared/middleware`.
- Keep environment access centralized in `src/config/env.ts`, except deliberate direct reads such as `process.env.BYPASS_AUTH`.
- Normalize employee emails before database queries.
- Return API responses as `{ success: boolean, data? | message? }`.
- Do not make frontend-specific imports in backend code. The current backend package contains some frontend-related packages, but backend source should stay server-only.
- Do not add database table names inline across multiple files. Keep table constants in repositories.
- Add tests before changing date boundary behavior or check-in/check-out rules.

## 12. AI AGENT GUIDE

This section is for Codex, ChatGPT, Claude, Cursor, Copilot, and other coding agents.

### How to modify safely

1. Read `src/modules/attendance/*` before changing attendance behavior.
2. Read `src/shared/middleware/jwt.middleware.ts` before touching auth or `req.auth`.
3. Do not edit `.env`; update `.env.example` and README instead.
4. Run `npm run typecheck` after TypeScript changes.
5. Run `npm run build` before claiming production readiness.
6. If changing Docker behavior, validate that `dist/server.js` is still the production entry.

### Files requiring extra care

| File | Risk |
| --- | --- |
| `src/shared/middleware/jwt.middleware.ts` | A small change can bypass auth or reject valid Firebase/Logto tokens. |
| `src/modules/attendance/attendance.repository.ts` | Supabase column names and date filters must match real schema. |
| `src/config/env.ts` | Adding required env vars can break startup if `.env` is not updated. |
| `Dockerfile` | Must compile TypeScript before copying `dist/` into runner. |

### Architectural constraints

- Attendance identity is email-based, not UID-based.
- Firebase account creation is not handled by backend.
- Supabase schema is not versioned in this repo; do not invent migrations in docs unless you also add real migration files.
- Current "today" logic uses UTC, not Asia/Bangkok local day.
- The API prefix is hardcoded as `/api/v1`.

### Forbidden or risky changes

- Do not replace Supabase with Firebase for attendance logs without a deliberate migration plan.
- Do not change `employee_email` to Firebase UID unless frontend, backend, and Supabase data all migrate together.
- Do not enable `BYPASS_AUTH=true` in production.
- Do not log Bearer tokens.

## 13. Common Problems

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| `envSchema.parse` throws on startup | Missing required `.env` values | Copy `.env.example` to `.env` and fill real values. |
| Frontend can hit `/health` but attendance routes return `401` | Missing/invalid Bearer token | Ensure frontend is logged in and sending Firebase ID token. |
| Attendance routes return dev user `test@company.com` | `BYPASS_AUTH=true` and no Authorization header | Send token or set `BYPASS_AUTH=false`. |
| Firebase tokens return `401` | `FIREBASE_PROJECT_ID` does not match frontend config | Align backend `FIREBASE_PROJECT_ID` with `src/config/firebase.js` projectId. |
| Supabase query errors | RLS policy or schema mismatch | Verify `attendance_logs` columns and anon key policies. |
| Duplicate check-in returns `409` | Employee already has today's UTC record | Check current row through `GET /today`. |
| Checkout returns `400` | No open row with `checkout_at IS NULL` | Check in before checkout. |
| Docker container starts then exits | Env file missing required values | Provide `.env` to docker-compose. |
